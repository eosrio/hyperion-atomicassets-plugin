# Royalty template list: pinned source oracle and capability boundary

Baseline: atomicassets-api 2.7.0 commit `0aabc47dcf8bd0804d4dcecb336c90fc02a9c89e`; the fixture verifies captured byte lengths, SHA-256 and Git blobs before evaluating original handler, validation, list resolver, builder, wrapper and route registration. The scripted DB returns supplied rows and records SQL/parameters; it does not execute PostgreSQL or model its errors, ordering, pagination or casting. Cache behavior is stubbed. This is not endpoint or physical parity qualification.

`template_id` is parsed before page and limit; non-string or empty means no membership. Comma-separated values expand `$list:name` once, preserve duplicates and accept `/^-?\d+$/` or case-insensitive `null`, which becomes the string `null`. Missing/empty lists remove membership; nested list references fail ID validation. Inputs including plus signs, decimals, whitespace and empty list entries fail with 400 before DB access. Values exceeding signed 64 bits still pass the source parser. The original builder emits scalar equality for one, `ANY` for 2–10, and `UNNEST` above 10; the latter casts to `BIGINT[]` only if all entries are weak integers, otherwise `TEXT[]`. Its variable deduplication can reuse a placeholder when numeric limit and offset match. Do not assume PostgreSQL cast or operator outcomes from this scripted control.

The handler constrains market and literal collection, orders by template ID ascending, and applies page/limit. `count`, sort, order and bounds are ignored; no template count route is implied. The original wrapper merges query then body (body wins); the control exercises POST and successful rows. The original validates page up to MAX_SAFE_INTEGER, but multiplication by limit can create an unsafe JavaScript offset. The exact original HTTP server, cache, transport and actual database error/timeout outcomes remain untested here.

A future backend-neutral capability must represent exact signed integer membership and numeric ordering, preserve original validation/list expansion and request fences, and execute one bounded indexed query. It must not coerce IDs through JavaScript Number, split into per-ID queries or silently scan. Compatibility for noncanonical values, literal `null`, signed-64 overflow, large cardinalities and unsafe offsets requires actual PostgreSQL-versus-target characterization before defining successful or error semantics. Native adapter execution, initialization/coverage, HTTP and cache acceptance are separate gates. No SDK, native backend or public route changes are made by this oracle.
